[1편](/posts/2017-04-14-jwt)에서 토큰 기반 인증의 개념과 트레이드오프를 살펴보았습니다. 이번 글에서는 **JWT(JSON Web Token, [RFC 7519](https://datatracker.ietf.org/doc/html/rfc7519))** 가 내부적으로 어떤 구조로 이루어져 있으며, 검증 과정에서 어떤 보안 함정을 조심해야 하는지 정리합니다.

## JWT의 전체 구조

JWT는 점(`.`)을 구분자로 하여 세 부분의 문자열이 연결된 형태입니다.

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IlN0ZXZlIiwiaWF0IjoxNzAwMDAwMDAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
└────────────── Header ──────────────┘ └─────────────────────────── Payload ───────────────────────────┘ └──────────────────── Signature ────────────────────┘
```

각 영역은 URL에서도 안전하게 전송할 수 있도록 일반 Base64가 아닌 **Base64Url 인코딩**(`+` → `-`, `/` → `_`, 패딩 `=` 제거)을 사용합니다.

## 1. Header (헤더)

토큰의 타입과 서명을 생성하는 데 사용된 **서명 알고리즘(JWS)** 정보를 담습니다.

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

- **`typ`**: 토큰 타입으로 보통 `"JWT"`를 지정합니다.
- **`alg`**: 무결성 검증에 사용할 서명/MAC 알고리즘입니다. 대칭키 기반인 **`HS256`(HMAC-SHA256)** 이나 비대칭키(공개키/개인키) 기반인 **`RS256`**, **`ES256`**, **`EdDSA`** 등이 널리 사용됩니다.

## 2. Payload (내용 / Claims)

실제로 전달할 사용자 정보와 토큰 메타데이터인 **클레임(Claim)** 이 JSON 객체 형태로 들어갑니다. 클레임은 세 가지로 분류됩니다.

### 등록된 클레임 (Registered Claims)

표준 스펙에 미리 예약된 선택적 필드들입니다.

- `iss` (Issuer): 토큰 발급자
- `sub` (Subject): 토큰의 주체 (보통 고유 사용자 ID)
- `aud` (Audience): 토큰의 수신 대상 서비스
- `exp` (Expiration Time): 만료 시각 (Unix Timestamp, 초 단위)
- `nbf` (Not Before): 토큰이 유효해지는 시작 시각
- `iat` (Issued At): 발급 시각
- `jti` (JWT ID): 토큰의 고유 식별자 (중복 사용/재생 공격 방지용)

### 공개 클레임 (Public Claims) & 비공개 클레임 (Private Claims)

- **공개 클레임**: 충돌을 막기 위해 URI 형식(예: `https://example.com/claims/role`) 등으로 이름을 정의합니다.
- **비공개 클레임**: 클라이언트와 서버 간 합의로 자유롭게 정의하는 사용자 정의 필드입니다.

```json
{
  "sub": "user_42",
  "role": "editor",
  "iat": 1700000000,
  "exp": 1700000900
}
```

> [!CAUTION]
> **JWT의 Payload는 암호화된 것이 아니라 단순 Base64Url 인코딩일 뿐입니다!**
> 누구든지 토큰 문자열을 디코딩하면 Payload 내용을 평문으로 그대로 읽을 수 있습니다. 따라서 비밀번호, 주민등록번호, 내부 API 키 같은 **민감 정보는 절대 JWT Payload에 담으면 안 됩니다.**

## 3. Signature (서명)

Header와 Payload가 전송 도중 **누군가에 의해 변조되지 않았음을 증명(무결성 검증)** 하는 영역입니다.

```js
const unsignedToken = `${base64UrlEncode(header)}.${base64UrlEncode(payload)}`;

// HS256 예시: 서버만 알고 있는 SECRET으로 HMAC 서명 생성
const signature = hmacSha256(unsignedToken, SECRET_KEY);
const jwt = `${unsignedToken}.${base64UrlEncode(signature)}`;
```

공격자가 Payload의 `"role": "member"`를 `"role": "admin"`으로 몰래 바꾸더라도 서버의 `SECRET_KEY`(또는 개인키)가 없다면 올바른 Signature를 다시 만들 수 없으므로 검증 단계에서 즉시 거부됩니다.

## 실무에서 반드시 막아야 할 JWT 보안 취약점

1. **`alg: none` 허용 차단**: 일부 구형 라이브러리에서는 헤더의 `alg`를 `"none"`으로 변조하고 서명을 비운 토큰을 유효하다고 통과시키는 취약점이 있었습니다. 검증 시 서버가 **허용할 알고리즘 목록(예: `algorithms: ["HS256"]` 또는 `["RS256"]`)을 반드시 명시적으로 고정**해야 합니다.
2. **비대칭키 환경의 Key Confusion 공격 방어**: 서버가 `RS256` 공개키로 검증하는데 공격자가 `alg`를 `HS256`으로 바꾸고 공개키를 HMAC 비밀키처럼 써서 서명하는 공격을 막기 위해, 검증 알고리즘을 한 가지로 강제하세요.
3. **충분한 비밀키 엔트로피**: `HS256`을 사용할 때는 최소 256비트(32바이트) 이상의 무작위 난수 비밀키를 사용해야 오프라인 무차별 대입 공격을 막을 수 있습니다.
4. **Payload 크기 최소화**: 토큰은 매 API 요청 헤더에 실리므로 꼭 필요한 최소한의 식별자(`sub`, `role`, `exp`)만 담는 것이 성능에 좋습니다.

## 핵심 요약

- JWT는 **Base64Url(Header) + `.` + Base64Url(Payload) + `.` + Signature** 로 구성됩니다.
- 서명은 **위·변조 방지(무결성)** 를 보장할 뿐 **기밀성(암호화)** 을 보장하지 않으므로 민감 데이터는 담지 마세요.
- 토큰 검증 라이브러리 호출 시에는 **허용 알고리즘(`HS256` / `RS256` 등)과 `exp`/`iss`/`aud` 검증을 명시적으로 활성화**해야 안전합니다.

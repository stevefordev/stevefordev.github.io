개발자가 기술 블로그를 시작하려 할 때 가장 먼저 마주치는 고민은 **"어디에 글을 쓸 것인가?"** 입니다. 네이버 블로그, 티스토리, 벨로그(Velog), 미디엄(Medium) 같은 호스팅형 플랫폼을 쓸 수도 있고, GitHub Pages 위에 직접 **정적 사이트 생성기(SSG: Static Site Generator)** 로 블로그를 구축할 수도 있습니다.

남들이 많이 쓴다고 무작정 정적 사이트 생성기(특히 과거 유행했던 Jekyll 등)를 선택하기 전에, **왜 SSG가 필요한지, 그리고 어떤 도구가 내 상황에 맞는지** 먼저 점검해 볼 필요가 있습니다.

## 정적 사이트 생성기(SSG)를 고르기 전 점검할 3가지

### 1. 내가 원하는 건 'Jekyll'인가, '정적 사이트'인가?

검색을 통해 블로그 만들기를 찾아보다 보면 특정 도구가 유행처럼 보이곤 합니다. 하지만 중요한 본질은 특정 툴 이름이 아니라 **정적 사이트 생성기(SSG)** 라는 아키텍처 자체입니다.

SSG는 작성한 마크다운(Markdown) 문서와 템플릿을 **빌드 타임에 미리 순수 HTML/CSS/JS 파일로 구워내는 도구**입니다. 덕분에 DB나 백엔드 서버 없이 GitHub Pages, Cloudflare Pages, Vercel, S3 같은 정적 호스팅에 무료로 올릴 수 있고 보안·속도 면에서 압도적으로 유리합니다.

Jekyll은 Ruby 기반의 대표적인 1세대 SSG일 뿐, 유일한 선택지가 아닙니다.

### 2. 커스터마이징 vs 글쓰기 집중의 균형

호스팅 플랫폼(벨로그, 티스토리, 미디엄 등) 대신 직접 블로그를 구축하는 가장 큰 이유는 두 가지입니다.

- **마크다운 파일과 데이터 소유권**: 플랫폼 서비스 종료나 정책 변경에 휘둘리지 않고 Git 저장소에 내 자산으로 영구 보관할 수 있습니다.
- **자유로운 커스터마이징**: 레이아웃, 코드 하이라이팅, 검색, 댓글(Giscus), 다크 모드, OG 이미지 자동 생성까지 내 입맛대로 설계할 수 있습니다.

반대로 단점도 명확합니다. **코드를 직접 관리하고 트러블슈팅하는 유지보수 비용**이 듭니다. 만약 UI 커스터마이징이나 프론트엔드 학습보다 *"오늘 당장 글쓰기에만 온전히 집중하는 것"* 이 최우선 목표라면, 처음부터 호스팅 플랫폼을 선택하는 편이 훨씬 꾸준히 글을 쓸 수 있습니다.

### 3. 내가 익숙한 기술 스택의 SSG 선택하기

블로그를 직접 운영하다 보면 언젠가 템플릿을 고치거나 플러그인 설정을 손대야 하는 순간이 반드시 옵니다. 이때 자신이 전혀 모르는 언어 기반의 도구를 고르면 사소한 수정 하나에도 큰 피로감을 느끼게 됩니다.

| 대표 SSG | 기반 언어 / 생태계 | 주요 특징 및 강점 |
| --- | --- | --- |
| **Jekyll** | Ruby | GitHub Pages 네이티브 통합 지원, 방대한 레거시 테마 (단, 로컬 Ruby 환경 관리가 번거로울 수 있음) |
| **Hugo** | Go | 단일 바이너리 설치, 수천 개 페이지도 수십 ms 내에 끝나는 압도적 빌드 속도 |
| **Astro** | TypeScript / JS | 콘텐츠 중심(Content Collections) 설계, 기본 Zero-JS 출력, React/Vue 등 원하는 UI 컴포넌트 선택적 결합 가능 |
| **Next.js / Gatsby** | React / JS | React 기반의 풍부한 인터랙션과 동적 앱 확장에 유리 |

> [!TIP]
> JavaScript/TypeScript 기반 웹 개발에 익숙하다면 Ruby 환경 설정이 필요한 Jekyll보다 **Astro**나 **Next.js** 계열 도구를 선택하는 편이 테마 커스터마이징과 장기 유지보수 측면에서 훨씬 수월합니다. 실제로 이 블로그 역시 과거 Jekyll 구조에서 **Astro(AstroPaper)** 로 이전해 관리 효율을 높였습니다.

## 결론

정적 사이트 생성기로 나만의 블로그를 구축하는 과정은 단순히 글쓰기 공간을 얻는 것을 넘어, **정보 구조 설계·빌드 파이프라인·배포 자동화·웹 성능 최적화**를 직접 경험할 수 있는 훌륭한 학습 프로젝트가 됩니다.

다만 도구 자체에 매몰되어 정작 첫 글을 쓰지 못하는 함정에 빠지지 않으려면:
1. "내게 정말 커스터마이징과 데이터 소유권이 필요한가?"를 먼저 묻고,
2. SSG를 쓰기로 결정했다면 **가장 익숙한 언어 생태계의 도구를 골라 빠르게 세팅한 뒤 글쓰기로 넘어가는 것**이 가장 좋은 선택입니다.

웹 애플리케이션의 사용자 경험이 데스크톱 앱 수준으로 높아지면서 **SPA(Single Page Application)** 는 프론트엔드 개발의 대표적인 아키텍처로 자리 잡았습니다. 하지만 모든 서비스에 SPA가 정답은 아닙니다. SPA가 내부적으로 어떻게 동작하며, 기존 MPA 및 현대적인 SSR/SSG와 어떤 차이가 있는지 살펴봅니다.

## MPA에서 SPA로의 진화

전통적인 **MPA(Multi Page Application)** 에서는 사용자가 링크를 클릭할 때마다 서버에 새로운 HTML 문서를 요청하고, 브라우저가 전체 페이지를 새로고침(Full Page Reload)합니다.

반면 **SPA**는 최초 진입 시 단일 HTML 껍데기(`index.html`)와 JavaScript 번들을 내려받은 뒤, 이후 화면 전환은 **서버에서 필요한 JSON 데이터만 비동기로 받아와 클라이언트에서 DOM을 교체**하는 방식입니다.

- **장점**: 페이지 깜빡임 없는 부드러운 전환, 네이티브 앱에 가까운 인터랙션, 프론트엔드-백엔드 API 분리
- **단점**: 초기 JavaScript 번들이 크면 첫 화면 표시(FCP/LCP)가 느려질 수 있고, 동적 메타태그·크롤러 대응(SEO)에 추가 설계가 필요함

## SPA 클라이언트 라우팅의 두 가지 원리

서버에 새 HTML을 요청하지 않고도 브라우저의 **주소창 URL을 바꾸면서 화면을 전환**하는 핵심 메커니즘은 두 가지입니다.

### 1. Hash 기반 라우팅 (`location.hash`)

URL의 `#` 뒤 부분(Fragment)이 바뀌어도 브라우저는 서버로 새 요청을 보내지 않고 `hashchange` 이벤트만 발생시킵니다.

```js
const routes = {
  "#/": "<h1>홈 페이지</h1>",
  "#/posts": "<h1>포스트 목록</h1>",
};

function renderByHash() {
  const app = document.getElementById("app");
  const hash = window.location.hash || "#/";
  app.innerHTML = routes[hash] ?? "<h1>404 Not Found</h1>";
}

window.addEventListener("hashchange", renderByHash);
window.addEventListener("DOMContentLoaded", renderByHash);
```

- 서버 설정 없이 정적 호스팅 어디서나 동작하지만, URL에 `#`이 붙어 깔끔하지 않고 서버가 경로를 인식하기 어렵습니다.

### 2. History API 기반 라우팅 (`pushState` / `popstate`)

HTML5 History API의 `history.pushState()`를 사용하면 페이지 새로고침 없이도 `/posts/1` 같은 **일반 경로 형태로 브라우저 주소창과 히스토리 스택을 조작**할 수 있습니다.

```js
const routes = {
  "/": "<h1>홈</h1>",
  "/about": "<h1>소개</h1>",
};

function render(pathname) {
  const app = document.getElementById("app");
  app.innerHTML = routes[pathname] ?? "<h1>404 Not Found</h1>";
}

function navigate(path) {
  window.history.pushState({}, "", path);
  render(path);
}

// 뒤로가기/앞으로가기 버튼 클릭 시 발생
window.addEventListener("popstate", () => {
  render(window.location.pathname);
});
```

> [!WARNING]
> History API 기반 SPA에서 `/about` 경로로 진입한 뒤 **새로고침**을 누르면 브라우저는 서버에 실제로 `/about` 파일을 요청합니다. 따라서 Nginx, AWS CloudFront, S3 등의 웹 서버에서 알 수 없는 경로를 모두 `/index.html`로 폴백(Fallback)하도록 설정해야 404 에러를 막을 수 있습니다. ([AWS 정적 웹앱 배포 가이드 참고](/posts/2017-06-08-aws-deploy))

## 렌더링 전략 비교: MPA · CSR · SSR · SSG

현대 웹에서는 순수 SPA(CSR)의 단점을 보완하기 위해 다양한 하이브리드 전략을 선택합니다.

| 전략 | HTML 생성 시점 | 초기 로딩(FCP) | SEO | 적합한 서비스 유형 |
| --- | --- | --- | --- | --- |
| **MPA (전통 서버 렌더링)** | 요청마다 서버 | 빠름 | 우수 | 단순 콘텐츠 사이트, 레거시 웹 |
| **CSR (순수 SPA)** | 브라우저(JS 실행 후) | 번들 크기에 비례해 느림 | 불리 | 대시보드, 백오피스, SaaS 앱 |
| **SSR (서버 사이드 렌더링)** | 요청마다 Node/Edge 서버 + Hydration | 빠름 | 우수 | 실시간 데이터가 중요하고 SEO가 필요한 서비스 |
| **SSG (정적 사이트 생성)** | 빌드 타임 (미리 HTML 생성) | 매우 빠름 | 우수 | 기술 블로그(Astro 등), 문서 사이트, 랜딩 페이지 |

## 핵심 요약

- SPA는 **클라이언트 라우팅(`pushState` / `hashchange`) + 비동기 데이터 페칭**을 조합해 매끄러운 화면 전환을 제공합니다.
- 기술 선택은 유행이 아니라 서비스의 성격(SEO 중요도, 인터랙션 복잡도, 데이터 실시간성)에 따라 CSR, SSR, SSG 중 가장 알맞은 조합을 고르는 것이 중요합니다.

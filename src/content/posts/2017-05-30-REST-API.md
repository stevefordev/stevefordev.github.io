현대 백엔드와 프론트엔드 협업의 공통 언어는 단연 **REST API**입니다. 하지만 단순히 JSON을 주고받는 HTTP API를 모두 RESTful하다고 부르기는 어렵습니다. 로이 필딩(Roy Fielding)이 2000년 박사 논문에서 제시한 **REST(REpresentational State Transfer)** 의 원래 의미와 HTTP 메서드의 정확한 성질을 짚어봅니다.

## REST란 무엇인가?

**REST(REpresentational State Transfer)** 는 웹(HTTP)의 장점을 최대한 활용할 수 있는 분산 하이퍼미디어 시스템 아키텍처 스타일입니다. 이름 그대로 **자원(Resource)을 이름으로 구분하여 해당 자원의 상태(Representation)를 주고받는 것**을 뜻합니다.

REST API는 크게 세 요소로 표현됩니다.

- **자원 (Resource)**: URI로 식별되는 대상 (예: `/users/42`, `/posts`)
- **행위 (Verb)**: HTTP 메서드 (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`)
- **표현 (Representation)**: 주고받는 데이터의 형식 (JSON, XML 등)

## HTTP 메서드의 올바른 사용과 Safe · 멱등성(Idempotency)

실무에서 가장 자주 헷갈리는 개념이 **Safe(안전성)** 와 **Idempotent(멱등성)** 입니다.

- **Safe(안전성)**: 요청을 보내더라도 **서버의 리소스 상태를 변경하지 않는 성질** (조회 전용)
- **Idempotent(멱등성)**: **동일한 요청을 1번 보내든 10번 보내든 서버의 최종 상태가 같게 유지되는 성질** (네트워크 장애 시 클라이언트가 안전하게 재시도할 수 있는지 판단하는 핵심 기준)

| 메서드 | 역할 | Request Body | Safe | Idempotent | 예시 |
| --- | --- | --- | --- | --- | --- |
| `GET` | 리소스 조회 | 사용 지양 (Query String 사용) | O | O | `GET /users?role=admin` |
| `POST` | 새 리소스 생성 / 처리 | O | X | X | `POST /users` |
| `PUT` | 리소스 **전체 교체** (없으면 생성 가능) | O | X | O | `PUT /users/42` |
| `PATCH` | 리소스 **부분 수정** | O | X | 구현에 따라 다름* | `PATCH /users/42` |
| `DELETE` | 리소스 삭제 | 보통 없음 | X | O | `DELETE /users/42` |

> [!NOTE]
> `PATCH`는 `{ "name": "Steve" }`처럼 특정 값으로 덮어쓰는 방식이면 멱등하지만, `{ "op": "increment", "field": "views" }`처럼 상대 연산을 전달하면 멱등하지 않을 수 있습니다. 반면 `PUT`은 리소스 전체 표현을 통째로 치환하므로 같은 요청을 여러 번 보내도 결과 상태가 동일하여 **항상 멱등**합니다.

### 흔한 안티패턴 피하기

- **GET 요청에 Body 실어 보내기**: 일부 도구에서 동작하더라도 HTTP 표준과 프록시·캐시 서버가 `GET` 바디를 무시하거나 차단할 수 있으므로 검색/필터 조건은 반드시 쿼리 파라미터(`GET /users?name=tom`)를 사용하세요.
- **GET 요청으로 서버 상태 변경하기**: `GET /posts/1`을 호출할 때마다 조회수가 오르는 정도는 실용적으로 허용되기도 하지만, `GET /posts/1/delete`처럼 조회용 메서드로 삭제·결제 상태를 바꾸면 크롤러나 브라우저 프리페치(Prefetch)에 의해 의도치 않은 부작용이 발생합니다.

## REST 아키텍처의 6가지 제약 조건

1. **클라이언트-서버 분리 (Client-Server)**: UI/사용자 상태 책임(클라이언트)과 데이터 저장/비즈니스 로직(서버)을 분리해 독립적으로 진화할 수 있게 합니다.
2. **무상태성 (Stateless)**: 서버는 클라이언트의 이전 요청 문맥을 저장하지 않으며, 모든 요청은 스스로를 해석하는 데 필요한 인증 토큰·파라미터를 온전히 포함해야 합니다. ([JWT 인증 글 참고](/posts/2017-04-14-jwt))
3. **캐시 가능성 (Cacheable)**: `Cache-Control`, `ETag`, `Last-Modified` 헤더를 통해 응답 재사용 여부를 명시하고 `304 Not Modified`로 불필요한 전송을 줄입니다.
4. **계층화 시스템 (Layered System)**: 클라이언트는 자신이 최종 서버에 직접 연결되었는지, 중간에 로드밸런서·API 게이트웨이·CDN·인증 프록시를 거치는지 알 필요가 없습니다.
5. **균일한 인터페이스 (Uniform Interface)**: URI 기반 자원 식별, HTTP 표준 메서드/상태 코드 활용, 자기 서술적 메시지(Self-descriptive), HATEOAS(응답에 다음 가능한 행동 링크 포함)로 클라이언트와 서버의 결합도를 낮춥니다.
6. **Code on Demand (선택 사항)**: 서버가 실행 가능한 스크립트(JS 등)를 내려주어 클라이언트 기능을 확장할 수 있습니다.

## 실무 URI 및 HTTP 상태 코드 가이드

### URI 설계 원칙

- URI에는 동사(`/getUsers`, `/createPost`)가 아니라 **명사형 복수 리소스**(`/users`, `/posts/12/comments`)를 사용합니다.
- 행위는 HTTP 메서드(`GET`, `POST`, `PATCH`, `DELETE`)로 표현합니다.
- 소문자와 하이픈(`-`)을 사용해 가독성을 유지하고, 끝에 불필요한 슬래시(`/`)는 통일합니다.

### 자주 쓰는 HTTP 상태 코드

- `200 OK`: 일반적인 조회/수정 성공
- `201 Created`: `POST` 등으로 새 리소스가 생성됨 (`Location` 헤더에 생성된 URI 반환 권장)
- `204 No Content`: `DELETE` 등 성공했으나 응답 본문(Body)이 없음
- `400 Bad Request`: 잘못된 요청 문법 또는 유효성 검증 실패
- `401 Unauthorized`: 인증되지 않음 (유효한 인증 자격 증명 없음)
- `403 Forbidden`: 인증은 되었으나 해당 리소스에 대한 권한이 없음
- `404 Not Found`: 요청한 리소스가 존재하지 않음
- `409 Conflict`: 리소스 상태 충돌 (예: 이미 가입된 이메일로 중복 생성 시도)

## 핵심 요약

- REST는 **REpresentational State Transfer**의 약자로, 자원(URI) · 행위(HTTP Method) · 표현(JSON 등)을 일관된 HTTP 표준 위에 올리는 아키텍처입니다.
- **Safe(`GET`)** 와 **Idempotent(`GET`, `PUT`, `DELETE`)** 의 차이를 정확히 지켜야 재시도, 캐싱, 프록시 처리가 안전한 API를 설계할 수 있습니다.
